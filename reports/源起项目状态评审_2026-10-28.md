## 1. 项目概览与架构

源起（影策）是 `ddcat-ai/open-ai-canvas`（开源 AI 创作画布）的深度二次开发版，面向国内电商/短剧/直播内容生产场景。三进程架构：

| 进程 | 端口 | 技术栈 | 职责 |
|---|---|---|---|
| Go 后端 | :8080 | gin + gorm + glebarez/sqlite（纯 Go 驱动，WAL） | 业务全部逻辑、任务编排、Agent 工具注册表、schema 迁移 |
| Web 前端 | :3000 | React 18 + Vite + antd + tailwind，bun 包管理 | 自由画布、各业务工作台 |
| nxf 影像引擎 | :8823 | FastAPI + torch/cv2/onnxruntime（Python venv） | BiRefNet 精细抠图（224MB 权重）、LaMa 局部重绘（208MB）、合成/打光/PSD |

统一控制台 `yuanqi_console.py`（:17580）编排三进程启停。本机 GPU 为 MX350 2GB，onnxruntime-DMA(DML) 提供者在本机有环境级 bug（区域编码崩溃），已实现自动探测 + CPU 回退 + 失败记忆。

**分支模型**：本地 fork `itsWyatt-K/open-ai-canvas`（可推送）；上游 `ddcat-ai/open-ai-canvas`（只读，推送被显式禁用）。所有开发在吸收车道 `absorb/upstream-v1.6.9` 上进行。

## 3. 上游情况与吸收机制

### 3.1 上游动态（ddcat-ai/open-ai-canvas）

上游 v1.7.2（2026-10-27/28，`d77e977a9`），开发方向：

5. README 产品化重写（内测预告）

节奏约每 1-2 周 1 个 minor tag，每次带 1-3 条 schema 迁移。

### 3.2 吸收状态：v1.6.8.12 → v1.7.2 已全部合入

六刀合并，每次全绿后推送：
`v1.6.8.12`(stage-1) → `v1.6.9`(Schema 64) → `v1.6.9.1`(65) → `v1.6.9.2`(66) → `v1.7.0`(67-77) → `v1.7.1+main`(78) → **`v1.7.2`(79-80，本轮)**

### 3.3 号段条约（吸收机制核心，防 schema 冲突）

上游与本地都在追加迁移，version 号会撞。现行条约：
- 本地 50-66 号段已 applied，**严禁改动**（真库 278MB 不可重放）
- 上游新迁移按 **"+6 平移"** 重编号（v1.7.0 时定下：上游 61-71 → 本地 67-77；v1.7.2 的 73/74 → 79/80）
- **checksum 字符串保留上游原串**（如 `sha256:drama-segment-references-v74-20261027` 落在本地 80 号），只移 version 字段——保留与上游的可追溯性
- 不变量：`CurrentSchemaVersion == schemaMigrations 末项 version`
- 每次合并前：实库 sidecar 备份（本轮 `bak-before-v172-s80`）→ 合并 → `migrate-schema up/verify` 实库 → 分片门禁

**本轮冲突面实测**：8 个上游提交只产生 2 个文件冲突（migrations.go 重编号 + segment-dialog.tsx 签名/import 并集），高危文件 user-data-sync.ts（本地三段式节流 vs 上游并发重放）自动并集成功。

## 5. 待优化事项（工程/性能/安全）

### 5.1 安全（软件工程审查已出清单，待拍板整改）
1. **nxf :8823 无鉴权 + CORS `*` + SSRF 面**：影像引擎接口可被任意本机进程/页面调用，且接受任意 image URL（服务端请求伪造面）。整改方向：loopback 绑定 + 本地 token + URL 白名单。
2. **两处明文 API key**（`_ops/fix_step1_relay.py:31`、`_ops/接入大狗生图中转.py:31`）：一次性运维脚本，应移入环境变量。

### 5.2 工程
1. **Agent 工具 Schema 体积**：36 工具 43361 字节，预算门禁 36000 已放宽过一次；每加工具必压缩描述，长期需要"工具分包/按场景裁剪"机制。
2. **备份自动化**：目前是人工 sidecar 拷贝惯例，应做成控制台启动前自动滚动备份（保留 N 份）。
3. **前端测试未纳入分片门禁**：bun/vitest 测试游离在 go 分片门禁外，本次 6 个存量红点即因此漏网。
4. **SQLite 单机天花板**：实库 278MB 且单文件；上游已带 `migrate-sqlite-postgres` 工具，切换时机需要决策（多端协同需求出现时）。
5. **nxf GPU 利用率**：MX350 2GB 显存太小 + DML 坏，全程 CPU 跑权重；单张抠图 25 秒。需评估换卡或云端算力分流。

## 6. 前端界面优化专项（请评审重点看）

### 6.1 已完成的三轮返工（背景，避免重复建议）

用户曾判定界面是"后端工程师画界面"——能力藏在状态后面。已完成：
1. 透明分层显性化：商品透明主体资产卡常驻（原图 vs 棋盘格对比），精修台入口全天候可见（出图前后都能进）
2. 3:4 海报画廊：未出图屏也渲染"渐变底+透明商品+标题叠印"的海报草图卡，锁主体开关外露
3. 失败红墙 → 单行可折叠条；AI 文案剥离 markdown 裸符号；并发排队不再抛红字
4. 画布节点参数收进默认折叠"⚙️ 高级参数"；双入口导航（自由画布/固定模块）

### 6.2 当前前端界面短板（待优化清单，按用户痛感排序）

1. **电商分镜卡信息密度过载**：一张卡上叠 L1 企划卡（标题/副标题/场景/锁主体/换思路输入行）+ 状态徽标 + 版本角标 + 4 个操作按钮（图层精修/送画布/详细编辑/单独生成）。小屏（1366×768）下换行严重，按钮语义相近难区分。**方向：操作按钮收敛为"主操作+更多"，或按卡状态只显示相关操作。**
2. **图层精修台（LayerStudioWorkbench）交互复杂度高**：四工具（抠图/消除/打光/文字）+ 文字层双击改字 + 图层树 + 保存/导出 PNG/导出 PSD/按草图生成，小白第一次进入没有动线引导。**方向：首次进入的步骤气泡引导 / 工具卡片化。**
3. **直播工坊 live-studio 空壳感**：模块大厅第 3 卡进去后功能稀薄（MVP），AI 背景生成未接。**方向：接 AI 背景生成，或在模块大厅标注"内测中"管理预期。**
4. **模块大厅视觉层级平**：5 张等权重大卡，没有"最常用"动线暗示。**方向：使用频率感知排序或置顶。**
5. **渲染性能**：3:4 海报画廊 7 屏同屏 + 棋盘格 CSS 渐变 + 投影叠加，实机自动化截图时出现渲染压力超时（低配机明显）。**方向：视口外懒渲染 / 骨架屏降级。**
6. **加载态与空态不统一**：各工作台自造 loading（antd Spin / 自绘渐变 / 骨架混用），空态有的有引导有的空白。**方向：统一 EmptyState / LoadingState 组件族。**
7. **错误文案人性化不彻底**：AI 输出与后端错误已剥离 markdown，但仍有技术味文案直达用户（如"revision 冲突"类）。**方向：错误文案映射表（错误码→人话+建议动作）。**
8. **移动端/触屏零适配**：全部工作台按桌面设计，宽度 <1024 直接破版。当前用户群是否需要移动端请评审给出判断。

### 6.3 一个待评审裁决的交互哲学问题

电商链路现在有两条"再创作"通道：**A. 页内**（图层精修台/详细编辑/单独生成）与 **B. 画布内**（送画布后用画布原生工具）。是否会造成用户认知分裂？还是"页内做批量生产、画布做单张精修"的分工是合理的？
