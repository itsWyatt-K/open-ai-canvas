## 一、要解决什么问题

### 1.1 业务场景

抖音/小红书上的**宠物模仿人类**爆款视频（猫做饭、狗开车、兔子喝咖啡这类），以及更广义的**竞品广告复刻**。

核心诉求：看到一条爆款 → 用自己的产品/宠物/素材，复刻出一条结构相同但内容原创的视频 → 批量裂变。

### 1.2 三个真实难点

| 难点 | 为什么难 |
|---|---|
| **主体一致性** | 生成 10 条视频，得是同一条狗。模型不会自动保证 |
| **动作合理性** | 猫的身体结构做人类动作，容易崩 |
| **导演工艺难描述** | "第 3 秒放钩子""第 9 秒产品落地"——人能感觉到，但说不成模型能消化的语言 |

### 1.3 一个常见的错误假设

**"把参考视频和参考图直接发给视频模型就行了。"**

我们用本地代码实测证伪了一半：

| 模型 | 本地状态 | 视频参考上限 | 图片参考上限 | 提示词上限 |
|---|---|---|---|---|
| MiniMax H3（3 个型号） | ✅ 可用 | **0（不支持）** | 4 张 | 2000 字符 |
| Seedance 2.5 | ⛔ 禁用（渠道未启用、未配价） | 3 个 / 200MB / 30秒 | 9 张 | 4000 字符 |

**结论：本地主力模型 H3 根本不收视频参考。** 而即使换 Seedance 2.5，业界主流用法也不是"直接喂"——下文第 5 节有佐证。

## 二、核心方案：三层叠加

```
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层  提示词工程层（反推）                                   │
│  E-Reverse 侧车：对标视频 → 逐秒拆解 → 每镜头「提示词四件套」    │
└───────────────────────┬──────────────────────────────────────┘
                        │ 四件套 + 关键帧
                        ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 2 层  资产编排层（画布）                                     │
│  画布节点：分镜行（四件套）+ 参考图节点 + 参考视频节点           │
│  @ 提及机制把提示词与资产绑定                                   │
└───────────────────────┬──────────────────────────────────────┘
                        │ 提示词 + 参考图 + 参考视频
                        ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 3 层  生成层（模型）                                         │
│  Seedance 2.5（支持视频参考）/ H3（只吃图，用关键帧兜底）        │
└──────────────────────────────────────────────────────────────┘
```

**设计哲学**：三层各司其职，互不耦合。反推不依赖具体模型；画布不关心提示词哪来的；模型只拿到自己吃得下的输入。

#### 反推产出什么（关键）

`pft_schema.py` 里的 `SceneSegment`（场景段）带有 **M3 结构化导演字段**（2026-10-14 新增）：

```python
class SceneSegment:
    index: int
    start_ms: int                    # 场景起始（ffmpeg scene 检测实测）
    end_ms: int
    keyframe_path: str               # ★ 关键帧文件路径
    semantic_tags: List[str]         # VLM 语义标签
    # ---- M3 结构化导演字段 ----
    shot_type: str                   # 景别：微距特写/近景/中景/全景
    camera_movement: str             # 运镜：环绕慢运镜/极速推镜/固定机位
    visual_prompt: str               # ★ 客观画面物理描述（去修辞，供生图/生视频）
    compliance_prompt: str           # 防封通感隐喻改写版（敏感品类专用）
```

**这是「每镜头一份提示词工程四件套」**，不是给人看的分析报告。

- `SpeechSpan`：ASR 不可用时的降级产物（ffmpeg silencedetect 实测）
- `Provenance`：**溯源块，代码注释标了"强制，缺一不可（项目铁律：可回链）"**
- 设计纪律原文：「**provider 可插拔——ASR / VLM 均为外部能力，缺失时字段留空而非编造**」

画布还有两块现成积木：

### 3.3 ★ 最关键发现：两个已有结构几乎一一对应

画布批量表已有**分镜行**结构（`web/src/types/canvas.ts:110`）：

```typescript
export type StoryboardRow = {
    id: string;
    shotNumber: number;
    durationSeconds: number;
    plotDescription: string;        // 画面描述
    dialogue: string;               // 台词
    characters: StoryboardCharacterReference[];  // 角色引用
    narrativeIntent: string;        // 叙事意图
    viewerPOV: string;
    performanceBlocking: string;
    shotSize: string;               // 景别
    emotion: string;
    lightingAndAtmosphere: string;
    audioEffects: string;
    camera: string;                 // 运镜
    motion: string;                 // 运动
};
```

与 E-Reverse 的 `SceneSegment` 映射关系：

| E-Reverse `SceneSegment` | 画布 `StoryboardRow` | 说明 |
|---|---|---|
| `shot_type` | `shotSize` | 景别 |
| `camera_movement` | `camera` / `motion` | 运镜 |
| `visual_prompt` | `plotDescription` | 画面描述 |
| `(end_ms - start_ms)` | `durationSeconds` | 时长 |
| `WordStamp` 词级台词 | `dialogue` | 台词 |
| 钩子 / 叙事功能 | `narrativeIntent` | 叙事意图 |
| `keyframe_path` | → 参考图节点输入 | 关键帧当参考图 |
| `compliance_prompt` | （无对应，需新增或走 `plotDescription` 变体） | 防封改写 |

**这意味着 handoff 不是"新造一套东西"，而是"两个已有结构做字段映射"**，实施成本大幅低于原估。

## 五、市面对标（2026-10-29 检索）

| 平台 | 做法 | 本质 | 与我们的关系 |
|---|---|---|---|
| **LiblibAI** | ①「视频特效」模板：使用特效→上传图→**不用写提示词**→一键生成 ②「提示词反推」入口（**图片级**）③作品页「做同款」 | 模板化封装 | 反推是图片级，我们比它深一层（视频级逐秒） |
| **LibTV** | 「**复制项目**」：别人整套画布复制过来，含角色参考图/场景道具/音乐切片/分镜关系，再用 TV Director Agent 改 | 整套资产复制 | 最彻底但有版权风险，且依赖别人开放项目 |
| **可灵 AI** | 工具指南原话：「更适合**重新生成**，需要使用者**把参考视频拆成提示词、首尾帧或分镜**，而不是直接上传整段视频完成复刻」 | 提示词重建 | ★ **直接印证本方案范式** |
| **即梦 AI** | 先用参考视频提炼人物关系、色彩、镜头节奏，再文生图/图生视频/首尾帧重建 | 先提炼再重建 | 同范式 |
| **海螺 AI** | 把参考视频节奏拆成多个短镜头，分别生成再剪 | 分镜重建 | 同范式 |

### 5.1 一句决定性佐证

录咖的工具指南描述可灵时明确说：

> 「需要使用者**把参考视频拆成提示词、首尾帧或分镜**，而不是直接上传整段视频完成复刻。」

**即：连支持视频参考的模型，主流用法也是「先拆再生成」。** 这佐证了本方案不是过度设计。

### 5.2 一篇 2026 方法论文章的三个观点（直接命中设计）

1. **「过度依赖反推工具的原始输出，误以为一键生成等于完美复刻」是常见偏差**——反推结果是半成品，必须人工补充隐性细节（演员眼神变化、BGM 情绪转折点、画面留白的叙事功能）
   → 对应设计：方案保留人工编辑环节（画布分镜行可改），不做全自动
2. **法律边界**：复刻的正当性在于学**视听语言结构、节奏编排、视觉修辞手法**，不是照搬受版权保护的特定角色形象、原创剧情台词。自查方法：「替换掉所有具象元素后，叙事逻辑与情绪曲线依然成立 → 合法借鉴」
   → 对应设计：`SceneSegment.core_stance` 已写明天「结构、节奏、镜头、钩子可以学；台词、画面内容、品牌表达不可抄——学骨架不抄肉」
3. **反推提示词要主动剥离可识别的版权要素，聚焦方法论层面的提炼**
   → 对应设计：`visual_prompt` 是「客观画面物理描述（去修辞）」，本身就不含品牌/IP 元素

### 5.3 我们的差异化优势

| 能力 | Liblib 图片级反推 | 本地 E-Reverse |
|---|---|---|
| 反推粒度 | 单帧图片 → 提示词 | **整条视频逐秒拆解** |
| 台词 | 无 | **whisperx 词级 ASR**，精确到第几秒哪个字 |
| 场景切分 | 无 | ffmpeg scene 检测**实测** |
| 结构化程度 | 一段文本 | **每镜头四件套** |
| 敏感品类 | 无 | `compliance_prompt` 防封改写 |
| 溯源 | 无 | `Provenance` 强制块 |

## 六、当前缺口（诚实清单）

### 6.1 缺口一：handoff 最后一公里没接（核心缺口）

`web/src/pages/ereverse/handoff.ts` 的注释自己承认了：

> 「画布 / 短剧制片台 / 直播装修台的所有权不在本页，预填它们需要改其他成员负责的文件——**本轮一律不改**。退而方案：重负载写 localStorage 快照，URL 只带轻量标记，跳转前 toast 明确告知『已带入反推配方，请在节点中粘贴/选择』，**只有直播台参考图模块是真的自动预填**。」

实测：`EreverseHandoffShot` / `ereverse-handoff` 在画布侧 **grep 零命中**——消费端根本没接。

**但第 3.3 节说明：因为 `SceneSegment` → `StoryboardRow` 几乎一一对应，这个缺口的实施成本比原估低得多。**

### 6.2 缺口二：Seedance 2.5 渠道未启用

`CHANNEL_000011`：`enabled=0`、`price_configured=0`。需要启用 + 配 key + 配价。**这是方案的前置条件。**

### 6.3 缺口三：VLM 后端 2/4 不可用

`zhipu:glm-4v-flash` 与 `ollama:qwen2.5vl` 均 `available: false`。场景打标靠 Gemini + 本地 Qwen2.5-VL-3B 兜底，后者精度有限。

### 6.4 缺口四：H3 不支持视频参考

`maxVideos: 0` 是硬契约。用 H3 时只能走「关键帧 + 提示词」路径（这恰恰是反推的价值所在，但也意味着**反推是 H3 的唯一通路**）。

```
E-Reverse 反推完成
```

4. 批量表行数与模型调用的成本控制（8 镜头 × N 条裂变 = 8N 次生成）
