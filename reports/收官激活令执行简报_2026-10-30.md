## 一、「超时误判 401 登出级联」修复（根因定位 + 修复 + 实测生效）

**根因**（比报告 §3 的推测更精确）：级联源头是 `auth-session-hydrator.tsx` 的启动会话恢复——原实现把 `getAuthSession()` 的**任何**错误（网络抖动/超时/502/504/断网）都降级为匿名会话 → `RequireAuth` 踢到 /login。探针每次 `goto` 都是整页加载 → 每页都重跑 hydrator → 重负载下一次传输抖动就把整页打回登录页，表现为「铸会话被清场」的假象（服务端会话行其实一直有效——curl 直打始终 HTTP 200）。

**修复**（`4eb823e1b`）：严格按施工令铁律重写降级判定——
- **真实 401**（HTTP status / 业务 code / reason=unauthorized 任一命中）→ 唯一允许的降级匿名路径；
- **传输层失败**（无响应=超时断网、502/503/504）→ **绝不清除登录态**，800ms×2ⁿ 退避自动重试 3 次，耗尽后呈现「重试恢复会话」界面（保留本地登录态，绝不跳登录页）；
- 三态诊断埋点（rejected / transport_retry / transport_exhausted）可观测。

**实测生效**：修复后探针全程铸会话存活（此前 2-4 页后必崩），门禁从 15/21 → **18/21**，且 G0（采集有效性）与 G20（/omnireplica）首次同时点亮。全局唯一调用入口 `request.ts` 本身语义正确（无 response=可重试≠401），无需改动；运行中的登出仅剩三处显式用户动作（侧栏/资料页/登出钩子），无自动级联。

## 三、15s 预置模板 t_frame 基线实测（在线 :8823，产品特写模板扩时）

**口径**：15s @ 480p@24fps = 360 帧（3 镜 5s/5.5s/4.5s）；改稿 = 仅改 shot_2 标题文案（5.5s/15s，理论占比 36.7%）。

| 指标 | 全量渲染 | 局部改稿（R3 镜头级缓存） |
|---|---|---|
| wall 实测 | **45.6s** | **16.6s**（**提速 2.8×**） |
| stage_timings | validate 1ms / html 4ms / **capture 39057ms** / encode 6068ms | validate 1ms / html 1ms / **capture 15952ms** / encode 453ms |
| **t_frame 均摊** | **108.5 ms/帧**（render_log 口径） | 120.8 ms/帧（132 帧重截） |
| 帧数 | 360/360 | 132/132（**cache_hits=2**：shot_1/shot_3 复用，仅重截 shot_2） |
| 提交即见计划（R5 预报价） | recapture 3 / 预估 64s | recapture 1 + reuse 2 / **预估 21s**（实际 16.6s，报价保守成立） |
| credits_used | **0** | **0** |
| degraded | font_bold_mapped + stroke_clamped×4（诚实登记，不拒绝渲染） | 同左 |

**对照验收基线表（交付方案 §9）**：
- **改稿 ≤30s 头条指标：16.6s ✅ 达成**（E1 目标 t_frame≈100ms，实测 108.5ms——落在目标线上，承诺口径「成本与变更镜头时长成正比（典型 3 倍速）」成立；「快 5 倍」继续与 E1 深度优化绑定，不承诺）；
- capture 占墙钟 86%（39057/45600），html/validate 可忽略，encode 6s——后续优化主战场在截帧通道（jpeg q92 + optimizeForSpeed 的 `optimizeForSpeed` 参数生效核验建议列入 M1.1）；
- encode 改稿仅 453ms（vs 全量 6068ms）——**segment.mp4 concat 复装策略生效**（未变更镜头零重编码）。

实测脚本已入库：`nxf/_engine/yingce_bridge/benchmark_15s_baseline.py`（可重复跑，数据打 render_log.jsonl）。
